# devhouse

A portable **dev-house** for Claude Code: a co-PM orchestrator plus seven named specialist agents, with build, maintenance, and cold-adoption workflows and a fixed documentation standard. Packaged as a Claude Code plugin so it drops into any project.

## Session form (Claude Desktop only)

The same house can run as a **team of separate Claude Desktop sessions**, one per member, instead of one session dispatching subagents. Each member is a skill that a session loads to become that member. This needs **Claude Desktop**; in the CLI the protocol tells a skill to stop with a message (untried).

**It is heavy, by design for now.** The session form favours care over speed: every member carries the whole team protocol, every unit gets its full set of reviews and tests, and every hand-off goes through the manager. Even a small project takes hours and a lot of usage, mostly in the context each member re-reads on every turn. A lighter mode, with review depth set by the project's size, per-member rules and per-unit cost reports, is planned for the next version.

Each member has ranked values that shape what she notices and pushes on, and, if you turn it on (*Turning on crew memory* below), a small memory of how she works.

Remi, the release manager, audits what would ship for private data, checks text going out to people for the data and for how it will land, and never sends, posts or pushes. For an audit, ask Makima for "an audit only"; Remi writes her findings (class and location, never the value) to `<devhouse home>/release/<project>/`, outside the repo (protocol, *Release*). An audit-only file is never masked: it stays under `release/`, is never shipped, and an audit-only run reads no filter values file. She is invoked only when named (`@remi`), never by auto-dispatch.

**Outbound text.** Members draft; they do not send, except internal pull requests and PR or issue comments, with your approval, and the release push (below), which the manager makes (the orchestrator, in the subagent form). Text for people outside your organisation is drafted only, and you send it. A member posts an internal pull request or comment only on your approval for that act, in her own session, naming the repo, the PR or target and the draft version; the text then ends with `Generated by Claude <model>; posted with approval.` Other internal text (emails, chat, documents) is drafted only. A draft is saved under `<devhouse home>/outbound/<project>/`, outside the repo; it may hold client and personal data, so you delete it by hand, and nothing deletes it for you. It reaches you with Remi's review beside it (data right for this reader; how it will land). To mark a repo as internal, ask Makima (or the orchestrator) to record a line in the project's `CLAUDE.md`, one per repo:

```
outbound repos: <owner/name or remote URL>: internal
```

An unlisted repo is external. The rules are in `plugins/devhouse/team/protocol.md` (*Authority*, *Release*, *Outbound to people*); the reasons are in `Documentation/architecture/decisions/0012-outbound-to-people.md`.

**Releasing.** To release a version, ask Makima for a release of it (say, `0.2.1`) in her session, and give her the remote's URL.

- **What you provide.** The remote must be **created empty**, by you. Authentication is git's own (SSH or a credential helper), and a URL with credentials in it is refused. The project's `CLAUDE.md` needs a `release identity: <name> <<email>>` line, the name and email that author the public commit; Makima asks for one if it is missing. The version must not already be tagged, privately or on the remote. Git 2.45.3 or later is needed (checked when you ask for a release).
  - The version starts with a digit (e.g. `0.2.1`). An ended release's version can be retried as is once the old release has been ended (Makima records that), and resumes in the same folder.
  - No apostrophe in the project's path, the devhouse home, the remote URL or the release identity (so `O'Brien` cannot be the identity's name).
  - The remote is `https://`, `ssh://`, `user@host:path`, `file://` or an absolute local path (a relative one is refused). Plain `http://` and `git://` are refused. The URL must not begin with `-`, carry a password, or have a query string or a `#` fragment.
  - Fetches, `ls-remote` and the push never prompt, so cache the credentials or load the SSH key first, and sign in once before a first release (for GitHub, `gh auth login`). Put SSH key options in `~/.ssh/config`; a `core.sshCommand` in your global git config is used, one set only in the system config is not.
  - The push is **atomic** (both refs move, or neither), so the remote must support atomic pushes. GitHub, GitLab and `file://` do; a remote that does not refuses the push and nothing moves, and there is no non-atomic push, so use one that supports them.
  - A global `push.gpgSign=true` makes most remotes refuse the push; switch it off for the release.
  - Before the push, the URL you gave is checked against your git config: a global `url.<x>.insteadOf` or `pushInsteadOf` that would rewrite it, or a `pushurl` or `receivepack` set for the release's remote, stops the push (the message names only which test failed, never a key or a value), because the push would then go somewhere you did not approve. Fix your config, or end the release.
- **What happens.** A prep unit bumps the version and adds the release notes and the `CHANGELOG.md` entry that you approve. Remi then audits the release commit and builds a fresh public repo from it, and Shiro gives it a security pass. The push creates the public tag. A finding blocks the push, and only you waive it, except the three kinds below that nobody can waive.
- **What ships.** The tree without the process files: every `CLAUDE.md` and `CLAUDE.local.md`, `Documentation/brief/`, `Documentation/spec/`, `Documentation/dev-prompts/` and `.claude/`, in every release, with no opt-in. Those names are matched ignoring letter case, and `CLAUDE.md`, `CLAUDE.local.md` and `.claude/` are removed at any depth, not only at the top. The public history starts fresh, with one commit per release, each parented on the last, and nothing is ever force-pushed.
- **What stops a release.** A committed symlink or submodule, or a `filter=` attribute, stops it, and none of them can be waived: the only fix is removing it in the private repo. An `export-subst`, `export-ignore` or `ident` attribute stops it too, but you can waive each one per path. A project that needs Git LFS cannot use the release stage as it stands.
- **Permission prompts during a release.** In the default mode a release asks for many approvals: its `rm`, `tar`, write and `git` steps stop and ask, unless an allow rule of yours covers them (how many is unmeasured). It may run in any permission mode, and choosing "always allow" or switching modes does not end it. If you do approve prompts, the list of what to refuse is in the subagent form's last bullets below. In a mode that does not prompt, nobody checks Remi's, Shiro's or Dahlia's calls one by one (the stated limit, below).
- **The filter's values.** If a value must stay in the private repo but not ship, write `filter-values.txt` yourself, rather than typing the values in chat, because a chat stays in the session's transcript. In the subagent form you are the only writer of it: the orchestrator and Remi never write it. Its format is UTF-8 with no BOM, LF line endings only (Windows Notepad's default is CRLF, which the filter refuses), and one `value<TAB>replacement` per line, with no blank lines. A filtered release needs Python 3.8 or later.
- **The push.** Makima makes it, once per approval, after checking that what she pushes is what was audited: she asks you the push question (the P, the URL, `main` and the tag), and on your yes pushes from a fresh repository she makes for the purpose, never from the release's `public/` folder. Before every read or write of `public/`, whoever makes the call (Makima, Remi or Shiro) also checks that its `.git` is what the stage made, and a failed check stops the call and rebuilds the tree; the message names only which check failed. A full disk or a permissions problem (the check's scratch folder or reference repository) is not a rebuild: it goes to you. After a successful push Makima (the orchestrator, in the subagent form) asks you separately whether to tag the private commit, a tag that is never pushed. Anything else outward, such as `gh repo create` or `gh release create`, is yours.
- **The subagent form** ends the same way: the orchestrator makes the push on your yes, as Makima does. No command is handed to you. In a release the orchestrator takes Makima's place and Remi is dispatched for each of her steps (the drafts, the audits, the public tree, the manifest), doing what the release manager does in the session form. The charter holds the details (`plugins/devhouse/commands/devhouse.md`, *A release in the subagent form*); in your terms:
  - **Any permission mode.** The orchestrator does not ask for the mode, and does not end the release for a change of it, a "don't ask again" or an added folder. At entry it asks you to confirm the devhouse home, and waits. Before any dispatch it records a baseline (hashes of the checkout's git config, hooks and `.claude/`), and compares it before each push question; anything outside the expected set goes to you with which file or config record changed, by name, never its value, and **you decide** whether it matters. A rule added by "always allow" in `.claude/settings.local.json` is reported the same way and ends nothing.
  - **The stated limit.** In a mode that does not prompt, nobody checks Remi's, Shiro's or Dahlia's calls one by one: a subagent that has read untrusted release material holds `Bash` and `Write`, and what remains is the baseline, the orchestrator's own checks (the pin, the audit by SHA, the seal, the manifest), Shiro's pass and the push. The baseline covers only the checkout; a stray write anywhere else is compared by nothing, and only a path-shape scan of the transcripts may catch it. **The push is the same in every mode:** the orchestrator asks you the push question in chat and pushes once per yes.
  - **If you approve prompts.** Where the session prompts, a call outside what follows is refused, and "always allow" is your choice. Remi's legitimate calls are the protocol's own forms exactly as written, her read forms in `agents/remi.md`, and a `Write` only to the closed list of files in the charter (*Her `Write` targets*). **No argument ever holds text from R or P, a path included, and a pattern holds no `'`**; `diff` takes exactly two commits; `show` takes a blob SHA. On one of her read forms (`ls-tree`, `show`, `grep`, `log`, `diff`, `for-each-ref`), refuse `--no-index`, `-O`/`--open-files-in-pager`, `--output`, `--textconv`/`--ext-diff` without `no-`, `--filters` or `-f`. On any call, refuse a `git -c` or `--config-env` that is not in the protocol's own form, and refuse `git remote`, `git push`, `curl`, and a Read, Grep or Glob of `filter-values.txt` or of the release folder as a folder. Passing the file's path to the filter, or `test -f`, is part of the protocol's forms. A refused prompt stops her step; the orchestrator tells you, and you end the release or have the step dispatched again.
  - **What none of this closes** is reads. In a mode that does not prompt, with a folder added over the home, or where the crew-memory allow rules (`Bash(cat *)` and `Bash(grep *)`) are set, the values file is readable without a prompt; that stays the stated limit.

The record is kept in `<devhouse home>/release/<project>/`, outside the repo, and builds up there. The rules are in `plugins/devhouse/team/protocol.md` (*Release*, *The release stage*); the reasons are in `Documentation/architecture/decisions/0013-the-release-stage.md`.

**Bringing things in.** A member who needs to bring something in **to use** shows it to Shiro first: a new dependency or a version change, code copied from outside (a usage example from a doc page included), a repo or tool cloned to run, or any other file downloaded. Reading a web page for facts needs nothing, nor does reinstalling what your manifest and lock file already pin. Shiro answers in one abrupt line, pass or no, with as little as she thinks justifies it. If a member still needs something she refused, Makima asks her for a full report; a report that clears it is applied, and one that still says no comes to you, and only you overrule Shiro. When Shiro is not on the team, Makima asks you directly. It is a habit the team keeps, not something the plugin enforces (`Documentation/architecture/decisions/0016-research-intake.md` lists its limits).

- **It needs Python 3 and GNU tools** on the machine: `python` (3.9 or later; not the WindowsApps `python3` stub) and Git Bash on Windows, or GNU `mv`, `sha256sum` and `timeout` elsewhere. The plugin ships a small checker script that every intake runs; without a usable Python, an intake is a no, and so it is where only `python3` exists. Unpacking an archive also needs the Python patch release for its line (3.9.24, 3.10.19, 3.11.14, 3.12.12, 3.13.6, or 3.14.0 final and later, a later minor or major line only as a final release); older ones are refused. **For a Python package, Shiro's vulnerability scan needs `pip-audit` installed where plain `python -I` can import it** (`pip install pip-audit` into the Python the team runs, not a `pipx` or `pip install --user` copy); without it every Python intake reads as a missing scan. Any intake that contacts a remote (a clone, a look-up of a branch or tag) needs git with the July 2025 fixes (2.43.7, 2.44.4, 2.45.4, 2.46.4, 2.47.3, 2.48.2, 2.49.1, 2.50.1, or 2.51 and later).
- **Where things go.** Fetched material lives in the devhouse home, under `<devhouse home>/intake/<project>/items/`, never inside your checkout; a dependency is declared in the project's manifest and lock file; copied code goes into the project when it becomes part of it. `passed.md` in the same folder is the record of what passed, and it stays.
- **Turning it on for an existing project.** Makima asks once, and records `Intake start point: <sha>` in the project's `CLAUDE.md`: everything already there is accepted as it is.
- **A clone is checked before it is checked out,** from git's own listing of its tree, read as it comes from git and never saved (at most 500,000 entries, 2 GiB of files and a 320 MiB listing, with no name Windows or git would mishandle), so a clone refused at that point writes no listing file and no file of its tree (only git's own download stays, and the pass is void), and the clone and the checkout ignore your global git settings for line endings, hook folders and templates (a hook defined in git config itself, as `hook.<name>.command`, still runs). If a clone fails once checked out (the checker finds a link or a hard link, git cannot write a file, the checked-out commit is not the one asked for, or a file is missing), Makima tells you and records the pass as void. The checker's tests run against a real clone, which needs git 2.45.3 or later.
- **You delete these folders yourself,** and no member does: they hold clones and fetched material, and a hostile tree is not for a member to handle (the tool that guards removals may block it too). Until you delete a void clone, run no git command in it, and keep an IDE from opening it.
  - `<devhouse home>/intake/<project>/items/<name>-<id8>/repo`, after a void;
  - the rest of `items/`: a fetched download, a part-filled extraction, a leftover staging folder (`<name>-new-<n>/`) and a re-fetch (`<name>-<id8>-<n>/`);
  - `<devhouse home>/hidden-tests/<project>/<u>-intake/`: a hidden-set test's clones and material;
  - `<devhouse home>/verify/<project>-intake-<k>-sec/`: Shiro's own folder, which can hold a clone of what she read;
  - a leftover `fields.*` folder in the system temp folder, or under a `<u>-intake/` folder;
  - a leftover `tmp.*` folder in the system temp folder: a clone call that the tool killed (a timeout) can leave its index folder there.

**Stand up a team:** in a fresh Claude Desktop session, run bare `/devhouse` and answer **Sessions** to its question, or **Sessions in windows** to also have each member opened in her own window (the choice is kept as `member windows: on` or `off` in the project's `CLAUDE.md`). The session becomes Makima, the manager. She asks what the project is, recommends a folder and a new sidebar group, and on your approval founds the repo, moves in, files herself in the group (the group is the team), asks you six setup questions (the first, where to keep the files, only on a machine that has no home yet; one is what the team should call you, the last whether to turn crew memory on), and opens the planning set (planner, reviewer, security reviewer, designer, developer, tester and release manager). She opens the other members herself, as their work comes near; you may be asked to start one yourself, because the app asks you before a session starts in some cases. Set each member's session to the model shown above, since a skill cannot pin one.

**Or by hand:**

1. In the Claude Desktop sidebar, create a **group** for the team. The group is the team.
2. Open one session per member **in the project folder** (a session opened with no project folder gets its own scratch folder, and the team will not share a checkout).
3. File each session in the group.
4. In each, run its skill (`/devhouse:<role>`). The skill finds the teammates in the group, renames the session to its role title, and announces itself to the manager.
5. Give Makima (the manager) the task; she routes work to the others.

A session in no group is asked which group is the team. A member leaves by being archived, moved out of the group, or renamed. The rules members follow are in `plugins/devhouse/team/protocol.md`.

The team also talks to itself a little, and every member's turn-end to you is a line or two in her own voice. Each of these is short and starts no work of its own:

- **Praise:** at a unit's merge the manager says a word of praise to each member whose work went into it, usually inside the next pointer she sends anyway.
- **Drafting questions:** while drafting a work order the planner may ask a teammate, never the reviewer, a short question, and records the answer in the work order.
- **Teaching notes:** when the reviewer finds something in a member's work she may send that member a short note about the pattern to watch, after her review has gone to the manager. The member answers in one line.
- **An addressed post:** with crew memory on, the reviewer's hourly break-room post may be addressed to one teammate, who may answer in the file.

**How a unit runs.** Once the spec is locked, each build step (or maintenance task) is a **unit**:

1. Its work order gets Roxy's review, then Makima creates the unit's branch `work/<u>` and points the builders at it. Every member's session stays in the project folder; each builder works in **her own git worktree** under `.claude/worktrees/`, on her own branch (`work/<u>`, `design/<u>`, `tests/<u>`), and tells the other builders which shared files she will touch.
2. Tessa writes a **hidden set** of tests, outside every repo (under the devhouse home, by default `~/.devhouse/hidden-tests/`; see *Setting the devhouse home* below and the protocol's *Tests*), that tests the same requirements in a different manner. It is off limits to the developer and designer, and the protection is **detection, not prevention**: Roxy checks the code for special-casing of the hidden inputs, and Makima searches the builders' transcripts for access to it.
3. When every builder is done, Dahlia merges the branches and records a **frozen SHA**. Roxy reviews that exact SHA while Tessa runs the visible and hidden tests against it in a throwaway worktree, and, for a unit its work order marks security-relevant, Shiro reviews it for security (never reading the hidden set); a hidden failure is reported by requirement and class of input only. Blocking findings loop back to Dahlia, capped at three iterations.
4. After both passes, Tessa commits the hidden set, Dahlia re-freezes, and Roxy confirms it. Then Makima runs the git tripwire on the unit (*The git tripwire* below), asks **you** to approve the merge into the main branch, merges it (through the tripwire's script, not `git merge`), commits the unit's artefacts and cleans up. In hands-off she merges into `devhouse/hands-off` without asking, on your standing approval (manager skill, *Modes*).
5. While a unit is active, Roxy audits the team's files and git about every 15 minutes (missing reviews and security reviews, merges without review, missing tests) and reports each gap once. It pauses whenever the team waits on you.

The rules are in `plugins/devhouse/team/protocol.md` (*Units and branches*, *Tests*, *Check-ins*); the reasons are in `Documentation/architecture/decisions/0005-units-of-work-in-the-session-form.md`.

## What devhouse protects against, and what it does not

Devhouse defends against **accidents**, not against a hostile team member; an order for the hostile case is planned.

- **Accidents are covered.** A member, or something she read, adding a hook, a link, a filter, a submodule or a config value to your repo by mistake. The git tripwire (below) looks for those.
- **A hostile member is not.** In the session form every member has the Bash tool, as you, on your filesystem. Anything that needs someone to tamper with your `.git` on purpose (a file planted between a check and the command that follows it, a lock made at the right instant, a script edited in the plugin cache) is a stated limit, not something the team stops.
- **Prompt injection falls on the same side.** A member that follows injected text (a web page, a file, a dependency's README) and acts on it deliberately is the same as a hostile member, and is deferred with it. The tripwire catches what such text makes a member add by accident; it does not catch what it makes her do on purpose.
- **Some checks are defence in depth** (the hash of a submodule's inner git folder, the stop on a `commondir` file, the include checks, the re-checks for a link made late, the call form's scrubbing of the environment). They make accidents and clumsy tampering visible. They are not guarantees.

The rules are in `plugins/devhouse/team/protocol.md` (*The git tripwire*, *What it protects against, and what it does not*).

## The git tripwire

Some things in a repo change what git does, not just what the files say: a hook, a filter, a link, a submodule, a config value. A small script the plugin ships, `team/git-tripwire.sh`, looks for them in two places: what a unit (or one of the manager's commits) adds, and the shared checkout's own `.git`. It runs before every unit merge and every commit the manager makes, before the hands-off merges, and about every 15 minutes in Roxy's check-in wake. **It finds; it does not judge.** Shiro judges each hit (benign, or a blocking finding only you can waive), and you are asked when she is absent or the hit is under a `hidden/` folder. The manager and the orchestrator make their merges and commits through the script, not through `git merge` and `git commit`.

- **What you do.** Nothing, until it fires. Then the manager tells you in one line and Shiro judges; a released hit in the shared checkout's own `.git` is allowed from then on (the script remembers it in `<devhouse home>/tripwire/<project>/allowed`), and you are asked once whether to keep allowing it or remove it. Some hits are never allowed (anything that makes git load code, config or objects from somewhere, or hand a program or credentials to a remote); you are asked to remove those. Removal moves a file or folder into `<devhouse home>/tripwire/<project>/removed/`, which keeps it (a link is unlinked and logged there; a config key is unset, with its records saved when they hold no credential).
- **It needs** Git Bash (or bash 4 with GNU `sed`, `sort`, `find`, `cmp`, `gawk`, `sha256sum`, `ln`, `stat`, `mktemp`) and git 2.45.3 or later, and the devhouse home on a volume that supports hard links (NTFS, not exFAT). Without them every call stops with `git tripwire: call`.
- **If you set `XDG_CONFIG_HOME`,** it must be an absolute path in the `C:/…` form on Windows (not `C:\…`, not `/c/…`, not empty); any other form stops every call. If your Bash tool's environment sets `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM` or `GIT_ATTR_NOSYSTEM`, every call stops too: they send plain git to other files than the script reads.

### What it costs you

- **Git LFS, git-crypt, `nbstripout` and any other filter.** If your project uses a clean, smudge or process filter, **configured in any scope** (Git for Windows' own system config sets one for LFS), devhouse cannot merge a unit that writes a path that filter applies to, nor commit such a path. The script stops with nothing moved, because it runs git with every filter command switched off, and a merge or commit through that would store the file raw: the content a scrubbing filter was meant to remove would reach history. A unit that only deletes such a path merges. **You commit and merge those paths yourself, outside the team.** A global `nbstripout` means no `.ipynb` commit through the team. The check errs on the side of stopping: it also counts a symlink or a submodule path, a filter named `set`, `unset` or `unspecified`, a commit that only deletes a path, and a path another attribute source unsets.
- **Your project's own pre-commit guard is skipped.** `pre-commit`, husky, lefthook, or a plain `.git/hooks/pre-commit` (and `commit-msg`, `pre-merge-commit`, or a `core.hooksPath`) do not run on the team's commits and merges, because no hook runs in the script. The script prints a note when your project has one, and the manager passes it on: **run your guard yourself** before you push or release, and scan the commits since your last push, not only the files you have now. A guard run afterwards checks current files, not each commit: a secret that one unit commits and a later unit removes stays in the history you push, so it takes a history scan (a secrets scanner's history mode) of those commits. A husky project's local `core.hooksPath` is also a never-allowed config key, judged at every merge until you remove it; **removing it, or a plain `.git/hooks/pre-commit`, also stops your own hooks running for your own commits.**
- **A stale `.git/index.lock`** (a crashed or killed git, an antivirus scan), or a file another program held, stops a merge or commit with nothing moved, and says so. Delete the lock if no git is running. A background git (an editor's or a prompt's `git status`) takes the lock routinely, and one that lands between the script's check and its write leaves the branch moved and the index behind: the script's note says so. Once the lock is gone, run in the checkout (`<old>` is `<new>^`): after a commit, `git read-tree -m -i <new>` (it drops what you had staged); after a merge, `cd "$(git rev-parse --show-toplevel)" && git diff --name-only -z --no-renames --ignore-submodules=none <old> <new> | git --literal-pathspecs restore --source=<new> --staged --worktree --no-recurse-submodules --pathspec-from-file=- --pathspec-file-nul`, in Git Bash (an empty merge has nothing to restore, and `restore` then just says it needs a path), which keeps your other uncommitted changes. `git read-tree -m -u <old> <new>` fails once the merge has written any path.
- **A required filter and the index refresh.** While a filter is marked `required` (LFS is), a merge stops at the index refresh when a tracked file's stat data is stale, written in the same second as the index, or really changed. Run a plain `git status` outside the team, or commit or restore the changed filtered file.
- **A sparse checkout.** `core.sparseCheckout` in any scope, or any skip-worktree entry in the index (some people use `update-index --skip-worktree` to ignore a local config file), stops merges. Turn the sparse checkout off, or clear the bit: `git update-index --no-skip-worktree <path>`.
- **A pending merge, rebase or cherry-pick, or a staged index,** stops a merge or commit. Finish or abort it.
- **Some things hold every merge until they are removed or fixed by hand** (never released): a `config.worktree` or `extensions.worktreeConfig` (git sets it when anyone runs `git sparse-checkout`), a `hook.*` config key, and a submodule's own config with an include. A link under `.git` stops the call outright when it acts. A partial clone cannot merge, and `core.repositoryformatversion` and `extensions.*` are fixed by hand. **Other things are judged again at every merge** (never allowed, though a hit can be judged harmless and let through for one run): a hard-linked `.git` entry, a planted `core.hooksPath`, and the `modules` folder every project with submodules has under `.git`. If the `core.hooksPath` is your project's own (husky's), the team tells you once that it will fire at every merge and keeps it, because removing it would stop those hooks running for your own commits; ask for its removal if you want it gone.
- **Submodules.** A merge moves a submodule's pointer and never updates its work tree. Update it yourself. A project with submodules is judged at every merge (its `modules` hit fires each time), and that hit is kept: removing `modules/` would break your submodules.
- **A stop you cannot fix by reading the message.** A call that stops with `git tripwire: …` gives the label only, never a value: ask the manager, who has the protocol's list.
- **First units can be noisy.** A clone's own `remote.<name>.url`, `branch.<name>.remote` and `merge`, VS Code's `branch.<name>.vscode-merge-base` and a `pushurl` show once each, and you are asked once whether to keep each one. A stale `worktrees/<id>` entry is a hit until it is pruned. A unit that changes `.vscode/settings.json`, `.husky/`, `.pre-commit-config.yaml` or a `CLAUDE.md` below the root fires a hit.
- **A second machine, or a moved devhouse home,** has no salt there: calls stop until it is made, and every allowed hit fires again.
- **Day one in the subagent form.** The orchestrator records the home and makes the salt before its first checkpoint commit, Track 0's included.

### What to delete by hand

- `<devhouse home>/tripwire/<project>/removed/`: it can hold a credential (a moved config file, legacy remote or `modules/` folder). Nothing deletes it for you.
- A leftover `args.*/work.*/` folder under `<devhouse home>/tripwire/<project>/`: a call the tool killed (a timeout) leaves its scratch folder, which can hold a dump of your config.

The rules are in `plugins/devhouse/team/protocol.md` (*The git tripwire*); its tests are `bash tools/tests/git-tripwire/run.sh` in this repository (not installed).

From a Claude Code session:

```
/plugin marketplace add Cring-von-Conman/devhouse
```

Then `/devhouse` is available in every project on this machine. A session is a normal Claude Code session until you run `/devhouse`; the orchestrator role is opt-in and dormant by default.

### Setting the devhouse home

The session form keeps the tester's hidden sets and the throwaway verification worktrees (hers, and the security reviewer's) outside every repo, in the **devhouse home**. You choose it once per machine, by answering one question:

- The first time a team needs it on a machine, Makima asks where to keep the files. Say `default` for `~/.devhouse` (on the drive your user profile is on), or give her a folder (for example off a full C drive). She makes the folder, and records your choice in a small file, `~/.devhouse-home` (one line, outside every repo).
- Every later team on the machine uses the same home without asking.
- To change it later, ask Makima. It applies to every team on the machine, so she asks you to confirm. Running sessions keep their old home until they are re-pinned or reopened; a member opened afterwards whose project names the old home stops, loudly.
- She refuses a folder that is relative, a UNC path (`\\server\…`), inside a git work tree or a bare repository (she follows a link or a short name to the real folder, and refuses one that leads into either), inside `~/.claude` (or `%USERPROFILE%\.claude`, whatever `HOME` says), inside the Windows or Program Files folders, a drive root or your user home itself, or with any part of the path ending in a dot or a space, or holds a quote, a `:` after the drive letter, a `$`, a backtick, a control character, or an invisible text-direction or byte-order-mark character (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069, U+FEFF). She warns before using a folder under a cloud-sync folder (OneDrive) or on a network drive, since drafts and filter values would leave the machine. Don't track `.devhouse-home` in a dotfiles repo: a pull from another machine would rewrite it.
- *Your user home must be sound:* it must be an absolute `X:/…` folder, not a UNC path (`\\server\…`), and `~/.devhouse-home` must not be a link. The check cannot tell a mapped network drive letter (for example `H:`) from a local disk, so one passes; the network-drive warning (above) still covers a default home landing there. Every member checks this when she pins the home, **whatever the home's source** (setting `DEVHOUSE_HOME` does not get around it), and stops with `guard: user home` if it fails. To fix a relative or UNC user home, see *Advanced* (the only remedy there needs `USERPROFILE` to be a local `X:\…` path); for a `~/.devhouse-home` that is a link, delete the link yourself (nobody else may).
- *Fewer prompts (optional):* add `Read(~/.devhouse-home)` to your allow rules, since every member reads the pointer once a session, whether memory is on or not. If your `HOME` is a local folder other than your profile, Claude Code's `~` and Git Bash's differ, so the `~/` rules miss: that means extra prompts, not a hole.
- *Prompts from the home check (unmeasured):* each member checks the home when she first pins it, with one or two Bash calls that begin `fail() {`. None of the allow rules below matches them, so each member may meet one or two permission prompts at every pin, and a pending prompt blocks the turn, which matters most in hands-off. How many there are, and whether they appear at all, has not been measured.
- *In the single-session (subagent) form,* the orchestrator asks the same question (the default or a typed path, since there is no folder picker in this form), says which home the team will use, and records the `devhouse home:` line, and commits it, on your say before its first dispatch that carries the home.

**Advanced.** To pin the home yourself, set the environment variable `DEVHOUSE_HOME` to a literal absolute path, never `%USERPROFILE%`. It overrides the pointer, and Makima does not ask:

```
setx DEVHOUSE_HOME D:\devhouse
```

The variable is read when the Claude Desktop process starts, so set it, **fully quit Claude Desktop (including from the tray)**, and relaunch it; sessions reopened after that see it. Whether a full quit and relaunch is enough has not been measured. Changing the home later stops every team whose line names the old home, as each session re-pins.

To fix a user home that is relative or a UNC path (`\\server\…`), point `HOME` back at your local profile folder, and only if `USERPROFILE` is a local `X:\…` path (`echo %USERPROFILE%` in cmd, `$env:USERPROFILE` in PowerShell; a mapped network drive letter also looks like `X:\…`, so check the disk is local). Otherwise this README has no remedy: ask in the session. First note the current value of `HOME`, so you can put it back (an error here means none is set):

```
reg query HKCU\Environment /v HOME
```

Then, in cmd:

```
setx HOME "%USERPROFILE%"
```

In PowerShell:

```
setx HOME $env:USERPROFILE
```

Then fully quit Claude Desktop and relaunch it, as above. Whether that is enough for `HOME` too has not been measured.

Moving `HOME` changes Git Bash's home, so git's global config (your identity, `safe.directory`, signing), your `.ssh` keys and `known_hosts` are read from the new place; check they are there. To undo it, put back the value you noted (`setx HOME "<the old value>"`), or, if there was none, run this; then fully quit and relaunch again:

```
reg delete HKCU\Environment /v HOME /f
```

**Keep it out of allow rules.** Keep the home outside every folder that a project-level `Read` allow rule covers. A rule such as `Read(//d/projects/**)`, over `D:/projects/devhouse-home`, lets any session in that project read the home, the filter's values file included, without a prompt. At the start of a release the manager reads your settings files, read-only, and tells you about any rule of that kind; the crew-memory rules below are always among the ones she mentions. She never edits your settings.

The manager records the home once per project, as a `devhouse home:` line in the project's `CLAUDE.md` (`default` when the home is the default, `~/…` when it is under your user home, otherwise the absolute path), and every member checks her own pin against that line before she reads or writes there. The line is a tripwire, never the source: it arrives with the repo, so it cannot move your home. A member whose home differs stops and tells the manager; for crew memory alone (below) a mismatch, or a missing line, makes her skip the memory read or write instead of stopping, and she still reports a mismatch (a missing line is not reported during Project start). Makima then asks whether to move the project to this session's home, naming where each setting came from. Changing the home in a project that is running is between units, on your say; earlier units' hidden sets stay where they are. The rules are in `plugins/devhouse/team/protocol.md` (*Tests*, *The hidden set*).

**Clean-up.** The verification worktrees are removed after every run. The `hidden-tests/<project>/<u>/` folders are kept and build up after each merge; once a unit's `hidden/` folder is committed they are safe to delete, by you, by hand. The reviewer's `hidden-tests/<project>/<u>-validity/` folders build up too and are never committed. The `hidden-tests/<project>/<u>-intake/` folders (material the tester fetched for the hidden set) are never committed and are yours to delete. The `intake/<project>/items/` folders (fetched clones, downloads and staging folders) build up, are deleted by you, by hand, and `intake/<project>/passed.md` stays. The `outbound/<project>/` drafts, reader files and reviews build up too, may hold client and personal data, and are deleted by you, by hand. So do the `release/<project>/` record (the audits, the manifests, the `base-<k>` records of a subagent-form release, which hold private-repo content: commit subjects and a diff stat, or the full path list; and, under each version folder, `work/`, which holds the release commit's full path list and so is private-repo content, and `check-<n>/`, plus any leftover `tmp.*` folder that a killed call left in a version folder or in the system temp folder), the `public/` folder of each release and, if you used a filter, `filter-values.txt` (its values are the ones that must not ship). Nothing deletes any of them automatically.

### Turning on crew memory

Each member can keep a small memory of how she works, and the team shares a **break room**: a file where members post a line or two, in voice, and now and then send one another a short live message. It is **off by default**, and it has **two switches**, both yours:

- **(a)** the project's `CLAUDE.md` has the line `crew memory: on`. The manager asks whether to turn crew memory on as the last of her setup questions (memory is per project, so a project only feeds the vault once it is switched on); once you confirm that the allow rules below are in place, she makes the folder and records the line ("yes, but not set up yet" records nothing, and she asks again later). In the subagent form the orchestrator records it on your say. Without this line no member even checks for the folder, so nothing prompts.
- **(b)** the folder `<devhouse home>/crew/` exists. The manager makes it (the orchestrator in the subagent form), on your yes with the rules set; no other member creates it. There is one vault per machine, shared by every project, so the members learn from everything you work on. It is plain markdown, bounded (a full file is rolled into an `archive/` folder, and nothing is ever deleted for you).

A permission prompt still blocks a turn, so **set the allow rules first, then say yes**, above all before hands-off. The manager makes the folder and records the line.

1. Add the allow rules to your **user** settings file, `~/.claude/settings.json` (it applies to your Desktop Code-tab sessions; `/permissions` shows the active rules). These user-level rules apply in every Claude Code session on the machine, not only in devhouse projects. You edit it; devhouse never does. It is untested whether a multi-line `cat >> ... <<'DEVHOUSE_EOF_<n>'` append matches `Bash(cat *)`. The home check's own Bash calls begin `fail() {` and match none of these rules (*Setting the devhouse home*). If the file already has an `allow` array, merge these into it. For a home at `D:\devhouse`:

   ```
   {
     "permissions": {
       "allow": [
         "Read(//d/devhouse/crew/**)",
         "Edit(//d/devhouse/crew/**)",
         "Bash(cygpath -m *)",
         "Bash(test -d *)",
         "Bash(mkdir -p *)",
         "Bash(mv -n *)",
         "Bash(date -u *)",
         "Bash(cat *)",
         "Bash(grep *)",
         "Bash(wc *)",
         "Bash(tail *)",
         "PowerShell(Test-Path *)",
         "PowerShell(New-Item *)",
         "PowerShell(Move-Item *)",
         "PowerShell(Get-Date *)",
         "PowerShell(Get-Content *)",
         "PowerShell(Add-Content *)",
         "PowerShell(Select-String *)"
       ]
     }
   }
   ```

   For the default home, use `Read(~/.devhouse/crew/**)` and `Edit(~/.devhouse/crew/**)` in place of the first two. In a path rule `//` is absolute from the root (a Windows drive becomes `//d/...`, lowercase), `~/` is your home directory, and a `Write(...)` rule never matches, so `Edit(...)` covers writes. Bash and PowerShell rules match the command text only, so **they cannot be limited to a folder**: `cat` and `grep` are allowed everywhere while the rules are on, though a `>` or `>>` target is checked against the `Edit` rule. The PowerShell lines matter only to members who use PowerShell. Keep *Keep it out of allow rules* (above) in mind: `Bash(cat *)` and `Bash(grep *)` let any session read any file, the hidden sets included. The path-less rules `PowerShell(Move-Item *)`, `PowerShell(New-Item *)`, `Bash(mv -n *)` and `PowerShell(Add-Content *)` may also reach the machine pointer `~/.devhouse-home` (an append makes it refused, which is loud). Whether all four reach it has not been measured.
2. Then tell the manager (or the orchestrator in the subagent form) that the rules are set and to turn crew memory on, which is also your answer to her question. She makes `<devhouse home>/crew/`, and records `crew memory: on` in the project's `CLAUDE.md`, beside the `devhouse home:` line. There is no folder step for you.

To read it, open `<devhouse home>/crew/` as a vault in Obsidian; `breakroom.md` is the room and each member has a folder named for her. Memory is a record, never an authority: a note approves and waives nothing, and the break room says nothing about a review in progress. A denied read or write, or a failed home check, is skipped and never a blocker.

**Turning off.** To stop live messages, add the line `break room: file only` to the project's `CLAUDE.md`: the file stays and the messages stop. A recipient whose permission mode holds messages would show them to you, which is what this switch is for. To turn memory off, remove the `crew memory: on` line (or remove or rename the `crew/` folder).

The rules are in `plugins/devhouse/team/protocol.md` (*Crew memory*); the reasons are in `Documentation/architecture/decisions/0010-crew-memory-and-the-break-room.md`.

## How it works

- **`/devhouse`** convenes the house. In Claude Desktop it first asks **"Sessions or Subagents?"**, with three options: *Subagents* makes the main session the co-PM in **advisory mode** (reviews, drafts work orders, waits) until you say "run the loop"; *Sessions* enters the session form above, with the manager running the project from its start; *Sessions in windows* does the same and also opens each member in her own window. The choice is kept as a `member windows: on` or `member windows: off` line in the project's `CLAUDE.md`; ask the manager to change it at any time. In the CLI there is no question; it is the subagent form.
- **Three tracks** (see `commands/devhouse.md`):
  - **Build** — greenfield, one build-step at a time, human gate between steps.
  - **Maintenance** — discrete per-task changes to existing code.
  - **Track 0 — Onboarding** — one-time comprehensive documentation project when adopting a codebase cold.
- **Guardrails** throughout: human gate between steps/tasks (in the session form, hands-off mode is the one exception, between build steps only and on your standing approval; merging to the main branch and approving the spec still wait for you), 3-iteration cap, Roxy gates "done" (and Shiro, for security-relevant work), scope discipline, cheapest-sufficient model per role.
- **Documentation standard** — a fixed schema (required sections per doc, grounded-claims rule, Roxy checklist) that both tracks target, so "documented" is one checkable thing.
